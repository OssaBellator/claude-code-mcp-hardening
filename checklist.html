AI Coding Workspace Hardening Checklist

Use this before giving an AI coding agent broader repository, terminal, browser, cloud or deployment access. It applies to Claude Code, Codex, Cursor, Copilot, Cline, OpenCode, custom MCP servers and similar tooling.

1. Inventory the actual agent surface

  • List every coding agent, MCP server, plugin, extension, hook, skill, script and scheduled automation that can act on the workspace.
  • Remove tools that are no longer used or whose owner/purpose is unclear.
  • Record which tools are read-only, local-write, remote-read and remote-write.
  • Identify which components can execute arbitrary commands versus narrow reviewed capabilities.
  • Confirm each integration has a clear failure mode when its dependency or credential is missing.

2. Bound permissions

  • Default new integrations to the narrowest useful permission set.
  • Separate read-only inspection from write, deploy and publish operations.
  • Require an explicit step before destructive or externally visible actions.
  • Avoid production-admin credentials where a scoped service credential is sufficient.
  • Review logged-in browser automation separately from API access.

3. Protect credentials and customer data

  • Keep API keys and tokens out of prompts, repo files, issues, logs and screenshots.
  • Use a keychain, secret manager, encrypted credential store or provider-managed identity.
  • Prefer restricted/read-only keys for reporting and diagnostics.
  • Make credential rotation possible without editing source code.
  • Verify tool output does not echo authorization headers, environment variables or secret-bearing config.
  • Use synthetic or scrubbed fixtures instead of real customer data where possible.

4. Make repository instructions legible

  • Keep canonical agent instructions easy to find.
  • Remove contradictory or duplicated instruction files.
  • State build, test and lint commands explicitly.
  • State directories or files agents should not modify automatically.
  • Document external side effects such as deploys, emails, payments, account changes or PR creation.

5. Control automation and scheduled work

  • Give recurring jobs an owner, purpose, cadence and stop condition.
  • Bound retries and prefer idempotent actions.
  • Prevent stale jobs from silently resuming after restore unless intended.
  • Record enough state to distinguish never-ran, failed and completed.
  • Treat notification success separately from task success.

6. Reduce blast radius

  • Use a branch, worktree, container, sandbox or restricted route for risky changes.
  • Separate production deployment credentials from ordinary development credentials.
  • Prefer reversible changes and staged rollouts.
  • Avoid unattended force-push, force-reset, mass deletion or broad account changes.
  • Bound output size, runtime, recursion, destinations and action counts where practical.

7. Build recovery before you need it

  • Know how to restore the repository to a known-good commit.
  • Preserve important local-only state separately from the working tree.
  • Document which credentials must be recreated on another machine.
  • Verify backups do not silently include reusable secret material.
  • Test at least one recovery path.

8. Verify the paths that matter

  • Run the real build, typecheck, lint and test commands after agent changes.
  • Test integrations with the least privilege they are supposed to use.
  • Confirm revoked credentials or failed dependencies fail closed.
  • Verify externally visible results independently rather than trusting a success line.
  • Separate checkout redirects from actual completed payment evidence.
  • Keep evidence concise enough for another person to review.

9. Leave a usable handoff

  • Summarize what changed and why.
  • List remaining manual steps.
  • Record credential locations without recording values.
  • Document recovery and known failure modes.
  • Remove temporary elevated permissions, debug endpoints and one-off bypasses.
