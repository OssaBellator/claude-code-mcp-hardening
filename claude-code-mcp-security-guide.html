Claude Code + MCP security and hardening guide

The main risk in an AI coding workspace is not that an agent can edit code. It is that authority accumulates across several surfaces—repository instructions, persisted permissions, MCP servers, hooks, browser sessions, CI credentials and scheduled automation—until nobody can state what can act, with which credentials, against which systems, or how to recover if it fails.

This guide turns that problem into a reviewable operating model. It is grounded in Anthropic’s current Claude Code security, permissions, settings and MCP documentation, then extends those controls into practical repository and automation hygiene.

1. Inventory every authority surface

Start with a list, not a policy. Record every surface that can change files, execute commands, reach the network, use credentials, or trigger downstream work:

  • Claude Code repository instructions such as CLAUDE.md and shared settings;
  • other agent instructions such as AGENTS.md, Copilot instructions, Cursor/Windsurf rules and skills;
  • project and user MCP configurations;
  • hooks, plugins, commands, subagents and browser integrations;
  • GitHub Actions or other CI jobs;
  • scheduled/background agents and deployment automation.

For each item, classify authority as read-only, local-write, remote-read or remote-write. Then record the credential or identity that makes the action possible. A tool name alone does not tell you its blast radius.

2. Treat repository trust as a real boundary

Claude Code has workspace trust and separate approval behavior for project-scoped MCP servers. Anthropic also notes that non-interactive -p sessions do not show the same trust prompts. That means “the user would notice the prompt” is not a reliable control for every execution mode.

Before opening an unfamiliar repository with an agent that has meaningful authority:

  • Inspect repository-level agent settings, hooks and MCP configuration first.
  • Prefer a disposable clone, container, VM or low-privilege environment for untrusted code.
  • Do not assume a repository is safe because it only contains source code; project configuration can influence agent behavior before normal application code runs.
  • Separate evaluation of an unfamiliar repository from access to production credentials.

3. Make permissions explicit and review persisted rules

Claude Code supports allow, ask and deny rules. In Manual mode, many actions ask first; other modes change how approval is decided. A critical operational detail is persistence: some approvals can be saved to repository-local settings and apply to future sessions.

Review permissions with /permissions and answer three questions:

  1. Which rules are intentional?
  2. Which rules were added as a convenience workaround and now grant more than expected?
  3. Which actions should be denied rather than merely left to an approval prompt?

Prefer narrow tool/input rules over broad command families. A rule should express the smallest stable capability needed by the workflow, not the fastest way to silence prompts.

Prompt approval is not a sandbox. If a Bash command is approved and the process is not OS-restricted, it can act with the authority of the user account.

4. Use sandboxing for enforcement, not prompt text

Anthropic distinguishes the working-directory permission boundary from OS-level sandboxing. The former controls when Claude asks; the latter restricts filesystem and network access at execution time.

For higher-risk repositories or unattended work, define an execution boundary that remains true even when the model, a prompt, or an instruction file is wrong:

  • filesystem paths the agent may read and write;
  • network destinations it may reach;
  • commands or runtimes it may launch;
  • which credentials are present inside that boundary;
  • how generated artifacts leave the sandbox.

Use dev containers, VMs or other isolation where the consequence of a bad command is materially higher than the inconvenience of setup.

5. Audit the whole MCP surface

A project .mcp.json is useful evidence, but it is not the complete MCP inventory. Anthropic documents MCP servers at multiple scopes, plus servers introduced by plugins and connectors. A repository-only review can therefore miss authority loaded from outside the repo.

For every MCP server, record:

  • where it is configured and which sessions can load it;
  • who publishes or controls it;
  • what tools/resources it exposes;
  • whether operations are read-only or can mutate remote systems;
  • which token/account/identity it uses;
  • whether the credential is narrower than the human user’s normal account;
  • how the server fails when its dependency or credential is unavailable.

Anthropic recommends writing your own MCP servers or using providers you trust and notes that MCP servers are not automatically security-audited by Anthropic. Treat every server as code with authority, not as a harmless context plugin.

6. Separate credentials by purpose and blast radius

Credential isolation is one of the highest-leverage controls because it limits what a mistaken tool call can do.

  • Use read-only API keys for reporting and diagnostics when possible.
  • Separate development, deployment and production-admin credentials.
  • Keep secrets out of repository files, prompts, issue bodies, generated logs and screenshots.
  • Make credentials rotatable without source-code edits.
  • Prefer short-lived or provider-managed identity where available.
  • Test that tool output does not echo authorization headers, environment variables or secret-bearing config.

Do not treat “the agent was instructed not to print the token” as a credential control.

7. Bound hooks, CI and scheduled automation

Once a task can run without a person watching the terminal, the operating model needs explicit failure and recovery semantics.

For hooks, CI jobs and scheduled agents, define:

  • owner: who is responsible for the workflow;
  • trigger: exactly what causes it to run;
  • authority: what it can read/write locally and remotely;
  • idempotency: whether retrying can duplicate side effects;
  • retry bound: when it stops retrying;
  • state: how you distinguish never-ran, failed and completed;
  • stop condition: how the workflow is disabled or expires.

For GitHub Actions, keep repository permissions explicit, minimize write scopes, and pin security-sensitive third-party actions to reviewed immutable revisions where practical.

8. Design recovery before autonomy

A workflow is not operationally mature until recovery is known. Document and test:

  • the known-good Git commit or release to restore;
  • which local-only state must be preserved separately from the working tree;
  • which credentials must be recreated on another machine;
  • how a scheduled job is prevented from replaying stale work after restore;
  • how externally visible side effects are reconciled after a partial failure.

Prefer reversible changes, small batches and staged rollout. An agent can move quickly; recovery needs to be faster than the rate at which it can amplify a mistake.

9. Verify outcomes independently

Do not equate a tool’s success line with the final business outcome. Verify at the system boundary that matters:

  • run the actual build/test/lint/typecheck path after code changes;
  • fetch the deployed URL instead of trusting a deploy command;
  • check the remote repository after a push;
  • separate “checkout page loaded” from “payment completed”;
  • separate “notification sent” from “task succeeded.”

Keep the evidence concise enough that another person can review it later.

10. A practical minimum baseline

If you need a short starting point, make these statements true:

  • I can list every agent/MCP/hook/automation surface that acts on this workspace.
  • I know which of them can write locally or remotely.
  • I know which credential powers every remote action.
  • Production-admin credentials are not present in ordinary agent sessions unless explicitly required.
  • Repository-local permission rules are reviewed rather than accumulated indefinitely.
  • Risky execution has a real sandbox or disposable environment.
  • Scheduled work has bounded retries, state and a stop condition.
  • The repository has a tested build/verification path.
  • I know how to restore a known-good state.
  • I can verify externally visible results independently.
