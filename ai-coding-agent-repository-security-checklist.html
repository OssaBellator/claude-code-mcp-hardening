Before an AI coding agent acts on your repo, verify these boundaries.

Claude Code, Codex, Cursor, Copilot agent mode and other coding agents can cross boundaries that ordinary autocomplete never touched: shell execution, repository instructions, MCP tools, GitHub Actions, credentials, network access and remote writes. The checklist below is designed for one practical question: what should be explicit before you grant an agent real authority?

Why the repository itself is now part of the security boundary

OWASP's Secure Coding with AI guidance treats repository content, persistent rules files, MCP servers, CI/CD agents and developer permissions as trust boundaries in agentic coding. That matters because an agent can ingest issue text, pull-request descriptions, READMEs, rules files, tool descriptions and command output as context, then act with whatever authority the surrounding runtime gives it.

Microsoft makes a complementary point about MCP: the protocol standardizes tool discovery and execution, but does not itself provide a universal policy checkpoint that decides whether a particular agent should invoke a particular tool with particular arguments. In other words, tool availability is not the same thing as tool authorization.

The 10 checks

1. Inventory every persistent instruction surface

List the files that can steer future agent sessions: AGENTS.md, CLAUDE.md, Copilot instruction files, Cursor/Windsurf rules, hooks and any generated instruction layer. Decide which file is canonical and remove contradictory or abandoned copies.

Treat repository instructions as code-like authority: review changes, keep them scoped, and do not assume text is harmless because it is "only documentation."

2. Separate read authority from write authority

An agent that can read the repository is materially different from one that can edit files, execute arbitrary shell commands, push branches, modify workflows or call production APIs. Grant the smallest action set that accomplishes the task, and preserve explicit approval gates for irreversible or externally visible actions.

3. Audit MCP servers as privileged integrations

Record each MCP server, who operates it, which tools it exposes, what data it can access, whether calls are authenticated, and whether credentials are scoped to the minimum necessary capability. Anthropic's MCP tunnel security guidance recommends OAuth, narrow network reach, limited MCP server scope, credential protection and regular rotation. Those principles apply even when you are not using Anthropic's tunnel product.

4. Do not use model instructions as the only enforcement layer

A prompt that says "never call dangerous tools" is useful guidance, but it is not a deterministic authorization boundary. Microsoft recommends an explicit governance layer between tool discovery and execution so tool calls can be allowed, denied or require approval based on policy.

5. Protect credentials before the agent sees them

Keep long-lived secrets out of tracked files, agent-readable prompts and broadly inherited environment variables. Prefer scoped credentials and short-lived tokens where available. GitHub now exposes secret-scanning capabilities through its MCP server so supported AI coding agents can detect exposed credentials before code is pushed.

6. Review GitHub Actions as an agent execution environment

Pay special attention to workflow triggers, token permissions, use of pull_request_target, third-party actions, persistent credentials and any job that gives an agent access to organization or deployment secrets. A workflow triggered by untrusted issue or pull-request content deserves a stricter threat model than a developer-invoked local task.

7. Pin and verify third-party execution dependencies

Pin GitHub Actions and other executable integrations to immutable versions where practical. Verify AI-suggested packages before installation rather than assuming a generated dependency name is legitimate. OWASP specifically calls out hallucinated or typosquatted dependencies as an agentic coding risk.

8. Make recovery a first-class requirement

Before granting write authority, know how to undo the action: version-control rollback, branch protection, credential rotation, workflow disablement, deployment rollback and a tested path for restoring local configuration. A capable agent plus weak recovery is an operational risk even when no attacker is involved.

9. Verify outputs with independent checks

Builds, tests, linters, type checks, dependency scanners and secret scanning provide evidence that is independent of the model's own confidence. Do not let the same agent both define the acceptance test and silently weaken that test to make its change pass.

10. Keep an explicit human/accountability boundary

Decide which events still require a person: accepting contractual terms, moving money, rotating production credentials, merging privileged workflow changes, changing access control, publishing externally or deleting durable data. The faster the agent operates, the more important it is that these boundaries are obvious before execution begins.

A compact repository pre-flight

InstructionsOne canonical rules/instruction path; changes reviewed like code.
MCP/toolsKnown operator, authenticated access, least privilege and bounded arguments.
SecretsNo long-lived credentials in tracked files; scanning and rotation paths exist.
CIWorkflow triggers and token permissions do not give untrusted input unnecessary authority.
RecoveryRollback and credential-revocation steps are known before remote writes are enabled.
VerificationIndependent tests/scanners validate the result instead of relying on the agent's explanation.
