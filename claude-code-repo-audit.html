Repository audit methodology

How to audit a Claude Code / MCP repository without executing it

AI coding tools turn repository configuration into part of the effective control plane. A repo may contain agent instructions, MCP server definitions, hooks, GitHub Actions, browser/deployment integrations, local settings and recovery conventions. Before running any of it, you can learn a surprising amount from public or otherwise read-only evidence.

The core rule is simple: separate inspection from execution. An audit should not need to install the target repository’s dependencies, run its scripts, start its MCP servers, or grant it secrets just to understand how authority is wired.

1. Inventory the instruction surfaces

Start by locating the files that tell coding agents how to behave. Common examples include AGENTS.md, CLAUDE.md, GitHub Copilot instruction files, tool-specific command directories, and repository-local agent definitions.

The risk is not merely that an instruction file exists. The harder operational problem is instruction sprawl: several files can each appear authoritative while containing different build commands, permission expectations, or prohibited actions. Record every instruction surface and identify which one is canonical versus tool-specific.

2. Map MCP and agent settings without starting them

Look for repository-scoped MCP and agent configuration such as .mcp.json, mcp.json, .cursor/mcp.json, .vscode/mcp.json, Claude settings, and comparable tool files.

At this stage, do not launch a server named by the configuration. The useful questions are structural:

  • How many configuration surfaces exist?
  • Are the same servers declared in multiple places?
  • Are remote-write tools mixed into an otherwise read-only workflow?
  • Does configuration rely on hard-coded local paths or ambient credentials?
  • Can a reviewer tell which file actually wins when settings conflict?

3. Treat automation as authority, not just CI

GitHub Actions, hooks and scheduled jobs can hold more authority than an editor plugin. Inventory workflow files and inspect triggers, permissions and referenced actions. Review pull_request_target workflows carefully because they run in the base-repository context. Look for workflows that request broad write permissions when narrower scopes would work.

For referenced GitHub Actions, a full commit SHA is the strongest immutable reference. Tags and branches can be convenient, but they are movable references; use that fact as a hardening consideration rather than automatically calling every tag a vulnerability.

4. Look for credential-risk signals without printing credentials

A safe auditor should distinguish between evidence that deserves review and a verified secret exposure. A tracked .npmrc, for example, may contain harmless registry configuration. A tracked private-key file or a high-confidence live-token pattern is more urgent.

The output should report the affected path and the type of signal, not reproduce the secret value. If a live credential is confirmed in public history, rotation comes before cleanup.

5. Find the verification contract

Agents need a deterministic answer to “how do I know this change is good?” Look for explicit test, lint, typecheck, build or check commands. In a monorepo, those may be named test:unit, lint:ci or similar rather than only test.

If the verification command is ambiguous, an autonomous agent may choose the cheapest-looking command rather than the correct one. The audit should therefore treat legible verification as an operational control, not merely developer convenience.

6. Audit recovery before retry logic

Automation failures become expensive when nobody knows whether a half-finished action is safe to replay. A repository hardening review should ask:

  • Can a code change be restored to a known-good commit?
  • Are external writes idempotent, or can retrying duplicate them?
  • Is there durable evidence distinguishing “never ran,” “failed,” and “completed”?
  • Are scheduled jobs bounded by a stop condition?
  • Are production credentials separate from ordinary development credentials?

Recovery is particularly important for AI agents because a model can reason correctly about a task while still receiving an ambiguous transport or process result.

7. Preserve the evidence boundary in the report

A useful audit states what it actually inspected. For example:

  • repository tree entries inspected;
  • selected public configuration files read;
  • whether repository code was executed;
  • whether private repository access occurred;
  • known blind spots such as organization policy, runtime infrastructure or secret stores.

This prevents a filename-level or configuration-level review from being misrepresented as a penetration test or security certification.
