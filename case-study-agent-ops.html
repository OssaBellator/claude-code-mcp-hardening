Building a bounded AI-agent commerce and fulfillment workflow

This project started as a simple objective—turn an AI-assisted engineering stack into a revenue-capable service—and exposed the harder systems problem underneath: commerce, acquisition, delivery, privacy, permissions, recovery and verification all have to agree on the same operating boundary.

What was built

3live Stripe service tiers: A$39 public audit, A$79 60-day watch, A$149 hands-on hardening.
1zero-signup browser audit for public GitHub repositories.
1reusable GitHub Action + dependency-free CLI inventory tool.
9+public search/index surfaces submitted through a bounded IndexNow capability.

The engineering constraints

  • Do not expose the private Minimal MCP source tree to create a public offer.
  • Do not give the audit tool arbitrary command execution over customer repositories.
  • Do not collect payment/customer fields that are not needed for fulfillment.
  • Do not depend on a broken or stale hosting credential when a safer owned surface exists.
  • Do not treat “the deploy command succeeded” or “checkout loaded” as proof of the final outcome.
  • Do not silently send proposals, spend marketplace credits, or make other externally binding actions without the required authority.

1. Replace a broken deployment path with an owned public surface

The original offer domain was serving the wrong artifact. The hosting credential was also rejected as unauthorized, making blind redeployment unsafe. Rather than widen access, the project moved the public offer to a new isolated GitHub repository and GitHub Pages site containing only intentional public assets.

The public repository received a constrained README, checklist, landing pages, reusable Action, report methodology, sample report, sitemap, robots metadata and an IndexNow key. Private source and runtime state were explicitly excluded.

2. Turn the service into a product ladder

The offer was split by authority and fulfillment cost:

  • Free: browser/CLI/Action inventory with no target code execution.
  • A$39: deeper read-only audit of one public GitHub repository.
  • A$79: baseline, day-30 and day-60 public-repository reports.
  • A$149: hands-on audit and bounded implementation for one existing workspace.

This creates a path from zero-friction evidence to paid implementation without pretending every buyer needs private-repo access.

3. Build a narrow public-repository audit capability

The Minimal MCP GitHub provider was extended with a purpose-built read-only audit operation. It uses the GitHub API to inspect a bounded repository tree and selected public configuration files. It does not clone the target, install dependencies, execute build scripts, run workflows, or start MCP servers.

Current rule families include agent-instruction sprawl, multiple MCP configs, workflow surface, permissions: write-all, pull_request_target, movable third-party Action refs, secret-like tracked paths, basic quality-gate signals and public security-policy hygiene.

Validation: the capability was exercised against multiple unrelated public MCP/Claude repositories and against malformed repository inputs. Invalid targets fail before invoking GitHub.

4. Minimize paid intake

Stripe Payment Links collect only the fields required to deliver the public products: GitHub username, public repository URL and optional focus. Reporting omits checkout email, name, address and payment-method details.

Post-payment handoff URLs are fixed to the owned GitHub Pages site. During the audit, one live A$39 redirect was found pointing at an obsolete Pages project; the live Payment Link was repaired and re-read from Stripe to verify the change.

5. Automate fulfillment without leaking payment identifiers

Recurring fulfillment checks read paid intake, derive a one-way fulfillment key for public delivery, and avoid publishing raw Checkout Session IDs. The public report format separates:

  • evidence actually inspected;
  • review priorities from vulnerability claims;
  • positive controls from findings;
  • limitations caused by public-only evidence.

6. Add acquisition attribution without another analytics vendor

Paid CTAs use Stripe Payment Link client_reference_id values that contain only allowlisted placement codes such as free_audit_report and repo_audit_page. The reporting provider collapses unknown values to unattributed and aggregates sessions, completions, paid sessions and gross paid AUD by source.

No personal data is embedded in these source codes.

7. Make indexing repeatable

A dedicated Minimal MCP IndexNow capability now:

  • fetches the public verification-key file;
  • fetches the live sitemap;
  • rejects URLs outside the owned hardening-site prefix;
  • caps the submission at 100 URLs;
  • submits the bounded set to the official IndexNow endpoint.

The validation run returned HTTP 200 from IndexNow.

8. Verify the funnel at system boundaries

The public funnel was programmatically checked end-to-end:

  • every sitemap page returned HTTP 200;
  • every local CTA resolved;
  • all three Stripe checkout URLs returned HTTP 200;
  • the browser audit was exercised through managed Chromium against a real public repository;
  • GitHub Pages build status was checked independently;
  • Stripe aggregate reporting was read back after checkout changes.

Current commercial state

At the time this case study was written, the system had live products and observed checkout sessions but no completed paid sessions. That is intentional to state explicitly: this case study demonstrates engineering and operating-system capability, not fabricated revenue or customer outcomes.

What this demonstrates

This work is representative of the kind of engineering needed for AI-agent infrastructure that spans more than an LLM call: tool/provider design, permissions, GitHub automation, commerce APIs, privacy boundaries, public delivery, recurring jobs, failure recovery, observability and independent verification.
