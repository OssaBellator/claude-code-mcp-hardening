Practical guide · updated October 2026

Harden the repository around the coding agent—not just the code it writes.

AI coding agents add a second security surface around your application: repository instructions, permission rules, MCP servers, hooks, CI workflows, credentials and recovery paths. The checks below focus on that operating surface. They are intentionally narrower than a full application-security review.

1. Make the agent instruction surface explicit

Choose a canonical repository instruction file and document build, test, verification and forbidden-action boundaries. Multiple overlapping instruction surfaces are not automatically unsafe, but they are harder to review and easier to let drift.

Why: prompt instructions shape what an agent tries to do, but Claude Code's own documentation distinguishes those instructions from enforced permissions. Treat instructions as operating guidance, not an access-control mechanism.

2. Enforce authority with permissions, not prose

Review allow, ask and deny rules. Prefer the narrowest rules that support the workflow, especially for shell commands, network access and tools that mutate external systems. Avoid broad unattended authority unless the environment is deliberately isolated.

Vendor guidance: Claude Code supports fine-grained tool permissions; deny rules take precedence over ask and allow rules. Its documentation says bypassPermissions should be used only in isolated environments such as containers or VMs.

3. Inventory every MCP configuration scope

Do not assume a repository's .mcp.json is the complete MCP inventory. Check project, local, user, plugin, connector and managed sources where relevant. Remove duplicate or stale servers and document which definition is expected to win.

Vendor guidance: Claude Code currently supports local, project and user MCP scopes, plus plugin/connectors and managed configuration. Project-scoped servers live in .mcp.json, while local and user definitions can live outside the repository.

4. Keep credentials out of tracked configuration

Use environment-variable references or a secret store instead of literal tokens in repository files. Review tracked .env, credential, private-key and package-registry configuration paths. If a real credential ever becomes public, rotation matters more than merely deleting the current file.

5. Use hooks for deterministic guardrails

When a rule must be enforced every time—blocking a destructive command, protecting a path, or validating a tool input—prefer an enforcement mechanism such as a permission deny rule or PreToolUse hook over a natural-language reminder.

Vendor guidance: Claude Code's PreToolUse hook runs before tool execution and can allow, deny, ask or modify a call; its permissions documentation states that prompt instructions do not change what the runtime permits.

6. Sandbox high-authority shell execution

Separate “the model chose a command” from “the operating system allowed the command.” For risky automation, use filesystem/network isolation, a disposable worktree/container/VM, or another boundary that limits damage even when a command is approved incorrectly.

Vendor guidance: Anthropic documents sandboxed Bash with filesystem and network isolation and recommends VMs for scripts/tool calls involving untrusted or external content.

7. Give GitHub Actions the least privilege it needs

Declare explicit workflow/job permissions rather than inheriting broad defaults. Pay particular attention to workflows that publish releases, write issues, mutate repositories, or handle credentials.

8. Treat pull_request_target as privileged

Use it only when its base-repository trust context is actually required. Never combine privileged secrets/token access with checking out and executing untrusted pull-request code.

GitHub guidance: pull_request_target receives the base repository's trust, including a privileged token and potentially secrets. GitHub warns that checking out fork code and then executing it can create a “pwn request” vulnerability.

9. Pin security-sensitive third-party Actions

Review external uses: references. Moving tags and branches are convenient, but a reviewed full commit SHA is a stronger supply-chain boundary for sensitive workflows. Keep an update process so pinning does not become permanent staleness.

10. Define one reproducible verification path

Make the commands that prove a change safe obvious: tests, lint, typecheck, build, policy checks or integration tests. Agents should not have to infer the quality gate from scattered CI files.

11. Design recovery before autonomy

Know how to return to a known-good commit, restore important local-only state, recreate credentials on another machine, and stop or deduplicate recurring jobs. Test at least one recovery path instead of treating rollback as documentation-only.

12. Verify external effects independently

A successful CLI line is not proof of a successful deploy, payment, notification or publication. Fetch deployed URLs, verify Checkout Sessions rather than redirects, inspect created issues/PRs, and preserve just enough evidence for another person to review the result.

What a repository-only audit cannot prove

A public repository audit cannot see private settings, organization policy, user-scoped MCP servers, secret stores, runtime infrastructure, local session state, or what a tool actually does after connecting. It should be used for triage and hardening evidence—not as a security certification.
